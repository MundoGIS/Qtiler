How QtilerAuth works & why it is secure

QtilerAuth is the security layer for Qtiler. It adds users, roles, project ACLs, API keys, brute-force protection and a built-in proof-of-work captcha — all without sending any data to third parties.

1. Architecture

  • Express middleware mounted on every protected route. Authentication is evaluated per request.
  • Persistence in a local SQLite database (data/auth.db, WAL mode) — no external database required.
  • Project ACLs stored in data/project-access.json; users in data/auth-users.json (mirrored to SQLite).
  • Stateless JWT sessions signed with a server-side secret; revocation list (jti) stored in SQLite.

2. Authentication methods

  • Cookie session: HttpOnly, SameSite=Lax, Secure when behind HTTPS. Used by the dashboard and admin pages.
  • Bearer token (JWT): for SPA and external service-to-service callers.
  • Basic auth: standard HTTP basic for QGIS Desktop and OGC clients.
  • API key: per-user keys passed via ?api_key= or X-API-Key header for WMTS/WMS/WFS/VectorTiles clients.

3. Cryptography & secrets

  • Passwords: hashed with bcryptjs (cost 10). Plain-text passwords are never stored or logged.
  • API keys: stored as SHA-256 hashes. The plain key is shown only at creation; rotating produces a new value.
  • JWT: HMAC-SHA256, signed with AUTH_JWT_SECRET; revocable per jti.
  • Constant-time comparisons for secrets and HMAC signatures (crypto.timingSafeEqual).

4. Brute-force protection

  • Per-(user, IP) lockout window: defaults to 8 failed attempts in 15 minutes → 15 minute lockout with Retry-After.
  • Per-attempt audit row in SQLite (login_attempts) with timestamp, IP, user-agent and outcome — visible to administrators.
  • Lockout is scoped per (username, IP) so legitimate admins working from multiple offices are never globally locked out by a remote attacker.

5. Built-in proof-of-work captcha

  • Triggered automatically after the configured number of failed attempts (default 3) — never on a normal correct login.
  • 100% local: no Google reCAPTCHA, no Cloudflare Turnstile, no third-party JavaScript, no tracking. Safe for GDPR-sensitive deployments.
  • Server issues a stateless HMAC-signed challenge. The browser computes a SHA-256 nonce in WebCrypto until it finds N leading zero bits.
  • Difficulty is configurable via AUTH_CAPTCHA_POW_DIFFICULTY (default 18 ~ 1–2 s on a laptop). Cloudflare Turnstile, hCaptcha and Google reCAPTCHA are also supported as drop-in alternatives.

6. Project access control

  • Public projects: WMTS/WMS/WFS open to everybody — ideal for the public services your organisation already publishes.
  • Authenticated projects: any logged-in or API-keyed user may access.
  • Private projects: only the explicitly listed users (and admins) can access. Enforced at the route level for every OGC and tile call.
  • Copied service URLs can include api_key for QGIS Desktop, but the parameter is stripped from cached GetCapabilities responses to prevent leaks.

7. Transport & HTTP hardening

  • Strict HTTP headers via Helmet: HSTS, X-Content-Type-Options, X-Frame-Options, Referrer-Policy, Cross-Origin-Resource-Policy.
  • CORS allow-list configurable via AUTH_CORS_ALLOWLIST; same-origin by default.
  • Cache-Control: no-store on every response that may carry an api_key in its body.
  • Designed to run behind IIS / Apache / Nginx as a reverse proxy with TLS termination.

8. Privacy & data residency

  • All authentication state lives on your server. No SaaS dependency, no remote «phone home».
  • License validation is offline: an RSA-signed key file activated locally; the plugin verifies the signature without network access.
  • Compatible with Swedish/EU public-sector data residency requirements (data stays inside your perimeter).

9. Operations

  • Auditable login history visible from the admin UI (Login audit).
  • Single SQLite file to back up; safe to copy while the service runs (WAL mode).
  • Trial and commercial license states are clearly displayed; expired plugins are auto-disabled and the base server keeps running.

10. Configuration (.env)

All security parameters are loaded from the server .env file at startup. Restart Qtiler after changing any value. The data/ folder (users, ACLs, login audit, license) is the only state that changes at runtime through this admin UI.

  • AUTH_JWT_SECRET — HMAC secret for JWT sessions. Set to a long random value; rotating it invalidates every active session.
  • AUTH_LOGIN_MAX_ATTEMPTS=8, AUTH_LOGIN_WINDOW_SECONDS=900, AUTH_LOGIN_LOCKOUT_SECONDS=900 — brute-force lockout per (user, IP).
  • AUTH_LOGIN_CAPTCHA_AFTER=3 — failed attempts before a captcha is required on the next login.
  • AUTH_CAPTCHA_PROVIDER — pow (built-in, recommended), turnstile, hcaptcha, recaptcha, or empty to disable. External providers also need AUTH_CAPTCHA_SITE_KEY + AUTH_CAPTCHA_SECRET_KEY.
  • AUTH_CAPTCHA_POW_DIFFICULTY=18 — leading zero bits required for the built-in PoW. Raise to 20/22 to slow bots further (1–2 s → 4–30 s on a laptop). AUTH_CAPTCHA_POW_TTL_SECONDS=300 sets challenge lifetime.
  • AUTH_API_RATE_LIMIT_PER_MINUTE=0 — per-API-key rate limit. 0 = unlimited. Recommended in production: 600–2000.
  • QTILER_CORS_ALLOWED_ORIGINS — comma-separated allow-list (e.g. https://map.example.com,https://portal.example.com). Empty keeps the legacy permissive behavior. QTILER_CORS_ALLOW_CREDENTIALS=1 enables cookie sharing across listed origins.
  • QTILER_ENABLE_HSTS=1 — turn on HSTS (only behind HTTPS). QTILER_DISABLE_HELMET=1 — disables Helmet (NOT recommended). QTILER_ALLOW_FRAMING=1 allows the dashboard to be embedded.
  • QTILER_WMTS_REQUIRE_AUTH=1 — refuse anonymous WMTS GetCapabilities discovery; per-project capabilities still respect the public/authenticated/private flag.

Tip: the bundled .env.example documents every variable. Copy it as .env, set AUTH_JWT_SECRET to a long random string, and you have a hardened production baseline.

QtilerAuth README

QtilerAuth secures Qtiler deployments with users, roles, project access rules, and API-key based authentication for GIS/web clients.

  • Users and roles: create administrators and authenticated users, suspend accounts, rotate passwords and API keys.
  • Project permissions: mark projects as public/private and assign user-specific access from this backend.
  • Authentication methods: cookie session, bearer token, basic auth, and api_key query/header support.
  • Integration: copied WMTS/WMS/WFS/VectorTiles URLs can include api_key for QGIS and other external clients.
  • Persistence: user accounts, plugin trial state, and project access rules are stored in SQLite.
